## What you asked for, mapped to what shipped

### Issue 1 — "animations prang hindi nag reflect yun current animation nung hypr?"

> The preset dropdown always showed "Default (Current)" even when
> Hyprland was actually running a different animation config —
> especially after fresh installs or manual edits to animations.conf.

✓ `AnimationsPage.qml` now reads `~/.config/hypr/modules/animations.conf`
on startup AND watches it for changes. Reconciliation cascade:

1. **Fast path** — parse `# Generated by Zen Settings — preset: X`
   header (our own writer stamps this on every save)
2. **Content match** — normalize whitespace + drop comments, compare
   against each preset in the dict. Tolerates formatting drift.
3. **Custom fallback** — no match → synthesize a `Custom (External Edit)`
   entry at the top of the dropdown, showing the live config read-only
   in the preview pane + an orange banner with a one-click "Restore
   default" button.

File watcher (`FileView.watchChanges: true`) fires `_reconcileLiveConf()`
whenever animations.conf changes — so if you edit via `nvim` while
Settings is open, the dropdown updates in real time.

### Issue 2 — "yun scroll hindi ko na scroll till last"

> The last widget (PageFooter / Reset button) was being clipped at
> the bottom of the Animations page — you couldn't scroll far enough
> to reach it.

✓ Root cause: ScrollView's auto-computed `contentHeight` didn't
account for the ColumnLayout's `y: 24` offset AND the bottom spacer
was only 24px. The effective reachable bottom was:

```
ColumnLayout.height   (NOT ColumnLayout.y + ColumnLayout.height)
```

Fix: wrap the ColumnLayout in an `Item` with explicit `implicitHeight`:

```qml
Item {
    implicitWidth: root.availableWidth
    implicitHeight: contentCol.y + contentCol.implicitHeight + 48
    ColumnLayout { id: contentCol; x: 24; y: 24; /* ... */ }
}
```

Also added `contentWidth: availableWidth` to the ScrollView (matching
the BatterySettingsPage pattern) and bumped the trailing spacer from
24 → 48px for visual breathing room.

### Issue 3 — "brightness sa laptop dapat ma dedetect ayaw gumana nung brightness nung try ko sa rog ko"

> Brightness slider never appeared on your ROG laptop despite the
> hardware supporting backlight control.

✓ New singleton `BrightnessService.qml` — enumerates ALL entries under
`/sys/class/backlight/` instead of hardcoding `intel_backlight` (which
never exists on AMD/ROG). Vendor ranking:

| Vendor prefix      | Rank | Typical on                          |
|--------------------|------|-------------------------------------|
| `amdgpu_bl*`       | 100  | Modern AMD laptops (ROG AMD, etc.)  |
| `intel_backlight`  | 100  | Intel laptops                       |
| `nvidia_*`         |  90  | NVIDIA PRIME hybrids                |
| `asus::*`          |  80  | ASUS platform (screenpad, kbd)      |
| `acpi_video*`      |  40  | Generic ACPI fallback               |

On ROG Ally / Strix AMD / Zephyrus G14 → auto-picks `amdgpu_bl0`
(or `amdgpu_bl1`). On Intel/NVIDIA laptops → picks `intel_backlight`
or the equivalent.

**Multi-device support** — ASUS platforms typically expose additional
surfaces (screenpad, keyboard backlight) via `asus::*` entries. The
Battery & Power page now shows a device picker when >1 device is
detected so you can control each surface independently.

**Write path** — tries `brightnessctl --device=<n> set <pct>%`
first (uses systemd-logind, no udev rules needed). Falls back to
direct sysfs write if brightnessctl is missing. Logs a diagnostic
to the shell console if both fail.

### Issue 4 — "widget weather and system monitor kapag nag restart kunwari pinalitan ko color pag ka restart ko babalik sa default nanaman"

> Custom background colors for the weather and system monitor desktop
> widgets reverted to default after every shell restart. Text color
> (`colorMode` / `customColor`) survived, but background color
> (`weatherBg` / `sysmonBg`) didn't.

✓ Classic state-clobber bug in `DesktopWidgets.qml`. Two serializers
write to the same `widgets-state.json`:

- **WidgetsPage.qml → saveState()** — full schema, includes `weatherBg`
  and `sysmonBg`. Fires when user changes a setting in the Settings app.
- **DesktopWidgets.qml → posSaveTimer** — partial schema, was missing
  `weatherBg` / `sysmonBg`. Fires 500ms after any widget drag on the
  desktop overlay.

So the failure sequence was:

1. User sets weather bg to custom orange in Settings → full JSON written
   with `weatherBg: {mode: "custom", color: "#ff8800", opacity: 0.92}` ✓
2. User later drags the weather widget on desktop to reposition →
   `posSaveTimer` fires and overwrites the JSON with a partial payload
   that DROPS the `weatherBg` and `sysmonBg` fields ✗
3. Next shell restart → `_applyConfig()` reads the clobbered JSON →
   `if (s.weatherBg) { ... }` guard fails → widget falls back to
   default dark background

Fix: `DesktopWidgets.qml` posSaveTimer payload now includes both
`weatherBg` and `sysmonBg` objects, matching WidgetsPage.qml's schema
byte-for-byte.

**Testing note:** if your colors were already clobbered pre-upgrade,
the fix won't restore them automatically — the info is gone from disk.
Just re-set the colors in Settings → Widgets once; they'll stick this
time.

## What this hotfix does NOT do (deliberately — scope control)

1. **No brightness keybinds added.** Those already exist in
   `keybinds-update.conf` via `brightnessctl -e4 -n2 set 5%+` / `5%-`.
   They'll continue to work; Settings just now shows the UI for them.

2. **No udev rule installed.** If you want non-root sysfs writes
   without brightnessctl, add a custom rule yourself:
   ```
   # /etc/udev/rules.d/90-backlight.rules
   ACTION=="add", SUBSYSTEM=="backlight", \
     RUN+="/bin/chgrp video /sys/class/backlight/%k/brightness", \
     RUN+="/bin/chmod g+w /sys/class/backlight/%k/brightness"
   ```
   Recommended path: just `sudo pacman -S brightnessctl` — cleaner.

3. **No Bezier editor for animations.** ControlCenterBanner still
   marks "Animation Bezier Editor" as a future feature — same as 3.4.2.

4. **Animation preset dict not expanded.** 21 presets, same as 3.4.2.
   Adding new presets is orthogonal to this hotfix's reconciliation
   logic — any future preset will automatically participate in the
   content-match cascade.
